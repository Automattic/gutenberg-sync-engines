# B4 — The de-rtc commit-cadence dial

## What changed

The announce/commit inversion left de-rtc's commit cadence "a setting
away": commits already coalesce (dirty holds everything since the last
commit; one commit in flight). This branch adds the setting.

- **Setting** (`Settings → Collaboration`): "Distributed Editing commit
  cadence", stored as `gutenberg_sync_engines_de_rtc_commit_interval`
  (whole seconds, 0–300, default **0**). 0 keeps the settle cycle
  (pseudo-realtime); 10 is the Distributed Editing vision's
  save-and-sync operating point. Registered with `show_in_rest` so
  tests/tools can flip it.
- **Plumbing**: the plugin enqueue localizes
  `window._gutenbergSyncEnginesSettings.deRtcCommitIntervalMs` onto its
  own bundle (`wp_add_inline_script`) — the framework announcement is
  untouched.
- **Client** (`src/engines/de-rtc/session.ts`): `maybePropose()` gains a
  minimum-spacing gate AFTER every existing guard: if the last commit
  was built more recently than the dial allows, one timer re-enters at
  the boundary. The dial changes WHEN a commit is built, never what it
  contains; all correctness machinery (commit holds, quiet gates,
  incorporation, review) is upstream of the gate and unchanged. Timer
  cleaned up in `destroy()`.

## Diff shape

Three files + one test file, stacked on `loop/a14` (the current de-rtc
session state): `includes/admin/class-gutenberg-sync-engines-settings.php`
(option, sanitizer, field), `includes/class-gutenberg-sync-engines-plugin.php`
(inline settings script), `src/engines/de-rtc/session.ts` (the gate),
`tests/js/engines/de-rtc/announce.test.ts` (cadence test). No wire,
storage, or protocol change — a client-side scheduling knob.

## Verification

- Jest: new test pins the dial (first settle commits immediately;
  interim edits coalesce; the boundary releases ONE commit carrying
  them); full suite 528 green.
- phpcs clean on both PHP files; typecheck clean.
- Browser soak A/B (4-minute `soak-transport.mjs`, de-rtc/http-polling,
  3 windows, identical seeded workload, tests env):

  | per user-hour        | dial 0 | dial 10 | delta |
  | -------------------- | ------ | ------- | ----- |
  | client requests      | 4350   | 3675    | −16%  |
  | upload KB            | 5897   | 4179    | −29%  |
  | download KB          | 11316  | 9678    | −14%  |
  | server dispatch ms   | 47164  | 48690   | ~par  |

  Both runs fully converged (3.0 s convergence check), zero skipped
  bursts. The workload types in short bursts with think time; a
  continuous-typing workload would widen the deltas (more interim
  commits to coalesce). Note on V1.md's "save-sync-session runs at both
  defaults": the ENGINE benchmark's save-sync-session scenario models
  cadence inside the harness (server-side) and does not read this
  client dial, so the browser soak A/B above is the meaningful
  both-defaults comparison; run `npm run bench` for the engine-side
  save-sync-session shapes.

## The open product decision (yours)

The DEFAULT stays 0 (pseudo-realtime) in this proposal — peers see each
other's keystrokes at settle latency, matching the other engines'
feel. Setting 10 as the default would make de-rtc cheaper per user-hour
out of the box (numbers above) at the cost of ten-second peer
visibility. The dial is live either way; the description text on the
settings screen explains the trade in user terms.

## Open questions

1. Default 0 or 10? (The vision argues 10; parity-with-other-engines
   argues 0.)
2. Should the field hide when the active engine is not de-rtc? (It
   currently renders always, labeled "Distributed Editing (de-rtc)
   only".)
3. Cap 300 s: arbitrary; happy to change.
