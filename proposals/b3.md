# B3 — Pending-edit UI phase: inline block cards; panel goes summary-only

Branch: `loop/b3` (branched from the base branch; independent of the
de-rtc a13→a14→b4→b5 stack and of a2→a3→a15).
Status: awaiting-human.

## What changed and why

The review surface is rebuilt to the validated prototype's recorded
decisions (V1.md B3): **two verbs Adopt/Reject, one merged task per
block, no version chip, and the sidebar panel becomes a summary-only
index with resolution at the inline block card.** The behavior layer
(contest lifecycle, merge-not-stack folding, capability gates) was
already done; this is the editor-component phase that replaces the
interim review-panel routing.

## The diff's shape

**Subtree — `gutenberg/packages/editor/src/components/collaboration-review-panel/`**

- `markers.js` — the chip-and-expand `ConflictMarker` is replaced by
  `BlockCard`: a directly visible pending-edit card anchored to the
  block. Its exported `BlockCardBody` renders ONE merged task for every
  review group targeting the block (no per-group verb pairs, no count
  badge): merged attribution ("Your edit…" only when every item is
  local), de-duplicated reason sentences, joined pending-content
  summary, and the two verbs. Adopt resolves every item on the block as
  `restored`; Reject as `dismissed`. If ANY item requires approval,
  Adopt is reserved for unfiltered-HTML holders (the existing
  `canRestoreItems` gate; others see the hint and can only Reject). The
  parked-insertion `InsertionCard` (Approve/Discard) is untouched — its
  approval-gate vocabulary predates B3 and its card was already inline.
- `index.js` — the panel is now a summary-only index: groups whose
  block is live render without verbs (attribution links to the block,
  as before); only groups with no live anchor keep Adopt/Reject there,
  so an orphaned conflict never becomes unresolvable. "Discard all" is
  retired with the panel's resolution role.
- `review-group.js` — verbs relabeled Restore/Discard → Adopt/Reject
  (the capability hints re-worded to match); new `summaryOnly` prop
  suppresses the action row.
- `review-data.js` — new exported `itemAnchorClientId( item, maps )`
  (identity `targetId` wins; positional `targetIndex` is the fallback)
  and a `clientIdByIndex` map in `useReviewData` (top-level block index
  → clientId via `getBlockOrder()`).
- `style.scss` — the chip styles are replaced by the pending-card
  styles (same visual family as the insertion card).
- `packages/sync/src/types.ts` — `SyncReviewItem` gains optional
  `targetIndex?: number`, documented as the positional anchor of last
  resort.

**Plugin**

- `src/engines/de-rtc/engine.ts` — de-rtc review items now carry
  `targetIndex`: contests anchor at their block index, parked proposals
  at their first changed block. This is a real capability gain: de-rtc
  addresses blocks positionally (no syncIds), so its review items never
  anchored to the canvas before — the panel was its ONLY surface. With
  B3, de-rtc conflicts get inline cards like intent-log's.
  Property-conflict parks (no changed blocks) stay panel-only by
  construction.
- `tests/e2e/specs/collaboration-intent-log-engine.spec.ts` and
  `collaboration-de-rtc-engine.spec.ts` — the review-lane walkthroughs
  now exercise the new surface: assert the inline card is present with
  its verbs, assert the panel shows NO verbs for anchored conflicts
  (the summary-only contract), resolve through cards first and panel
  verbs only for unanchored leftovers, and assert cards/panel/notices
  all clear durably across reload.

## Open questions for the human

1. **Always-visible cards.** The prototype decision "resolution at the
   inline block card" is implemented as an always-open card (the chip
   was the thing the decision removed). With many simultaneous
   conflicts the canvas gets busy; if that reads as too loud in real
   use, the card could collapse to its attribution line after N are
   open — a UI-only refinement over the same structure.
2. **Insertion-card vocabulary.** Parked NEW-block proposals keep
   Approve/Discard (approval of untrusted markup is a genuinely
   different act from adopting a pending edit). Unify to Adopt/Reject
   if you'd rather have one verb pair everywhere.
3. **Merged-resolution granularity.** One merged task per block means
   one decision covers every parked group on that block (per the
   recorded decision). The panel's per-group rows remain visible as
   summaries, so a reviewer who wants finer grain can still see the
   parts — but cannot resolve them separately at the card. Acceptable?
4. **Upstreaming.** The subtree diff is one component directory plus a
   one-field type extension; the `targetIndex` anchor is the only
   cross-package contract change and is optional/additive.
