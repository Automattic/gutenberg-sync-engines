# B5 — Review resolutions over REST

Branch: `loop/b5` (stacked on `loop/b4` → `loop/a14` → `loop/a13`).
Status: awaiting-human.

## What changed and why

Review resolutions were the last MUTATING transport row in de-rtc: a
reviewer's Adopt/Reject decision traveled as a `resolved` row through the
advisory sync transport. This item moves the mutation to an authenticated
REST route, completing the strictest reading of the transport-is-advisory
inversion (V1.md B5). The transport still BROADCASTS the outcome — the
stamped `resolved` row the server appends is how peers and late joiners
close the review item — but the decision itself now arrives the same way
commits do: over REST, permission-checked, outside the row lane.

## The diff's shape

**Server**

- `includes/engines/de-rtc/class-wp-de-rtc-engine.php` — the resolution
  application (previously inline in `handle_updates`) is extracted into a
  private `apply_resolution()` shared by both lanes, plus a public
  `resolve_proposal( $room, $proposal_id, $resolution, $client_id )` that
  validates and applies one resolution against a freshly loaded ledger.
  The transport row path is UNCHANGED in behavior and stays accepted for
  legacy clients (`handle_updates` now calls the shared applier). A
  stranded docblock from the insertion point was re-attached to
  `load_review_ledger()`; no other movement.
- `includes/engines/de-rtc/class-wp-de-rtc-review-controller.php` (new) —
  `POST /wp-sync/v1/de-rtc/resolve` with `{ room, proposalId,
  resolution (enum restored|dismissed), client_id }`. Permission mirrors
  the transports (`current_user_can( 'edit_posts' )`). It applies the same
  engine-lineage fence the transport applies: a room stamped with another
  engine 409s (`rest_sync_engine_mismatch`). Unknown proposal ids ack
  idempotently (`status: resolved`, no row) — same as the row path.
- `includes/class-gutenberg-sync-engines-plugin.php` — requires the
  controller and hooks `rest_api_init` (the same registration pattern the
  diagnostics request log uses).

**Client**

- `src/engines/de-rtc/review.ts` — `DeRtcReviewState` gains
  `setRestResolver()`. `resolve()` still closes optimistically and
  resolves every superseded revision with the folded task; per id it now
  POSTs through the resolver when one is registered and falls back to the
  legacy transport row ONLY when the POST rejects (older servers 404 the
  route; both lanes ack idempotently, so a double delivery is harmless).
- `src/engines/de-rtc/commit.ts` — exports `hasDeRtcCommitRoute()`, the
  commit lane's existing postType gate (posts, pages).
- `src/engines/de-rtc/engine.ts` — wires the REST resolver at entity
  creation for commit-route types only, so the REST split follows the
  commit split exactly: types whose proposals ride the autosave endpoint
  also resolve over REST; collections/unsupported types keep the transport
  lane for both. The room string mirrors the providers' convention
  (`objectType:objectId`). The resolver is unwired on entity destroy.

## Wire/protocol impact

- New REST route (additive). No new row types; the `resolved` row keeps
  its exact shape and broadcast semantics.
- Legacy compatibility both directions: an old client's transport
  resolution row is still accepted; a new client against an old server
  falls back to that row automatically.
- One deliberate side effect shared with the transports: resolving
  against a never-seen room creates its storage post (the storage API's
  room lookup does that on ANY room access; the route is edit_posts-gated
  like the transports, so exposure is unchanged).

## Open questions for the human

1. **Gate choice:** the REST lane follows the commit-route gate
   (posts/pages). Alternative: wire it for every de-rtc entity type since
   the route itself is type-agnostic. Following the commit split keeps
   one story ("REST types are REST for all mutations") and keeps the
   existing transport-lane tests meaningful; flipping the gate later is a
   two-line change.
2. **Route namespace:** `wp-sync/v1/de-rtc/resolve` places an
   engine-specific route in the framework's `wp-sync` namespace, matching
   where the transports live. If the framework would rather engines own
   their namespaces, `gutenberg-sync-engines/v1` is the alternative.
3. **Retiring the legacy row path:** kept deliberately (old clients).
   A follow-up could reject transport `resolved` rows once clients are
   known-updated; that is a wire-behavior change and stays out of B5.
