# V1.md — Definition of done for gutenberg-sync-engines v1

This file is the frozen scope contract for the v1 loop. The loop reads it every
cycle; humans edit it. Rules:

- **An item is DONE when its acceptance commands pass and a fresh-context
  verifier confirms it.** The verifier sees only the diff, this file, and the
  command output — never the executor's narrative.
- **Lane A** items may be completed autonomously (implement, verify, commit to
  the item's worktree branch). **Lane B** items stop at a prepared branch plus
  a written proposal; a human approves before anything merges.
- **Maybe** items are not items: the loop never starts one, and v1 can be
  declared with all of them still undecided.
- Scope changes to this file are always Lane B. If an item turns out to need a
  Lane-B surface (see "Escalation triggers"), the loop reclassifies it, parks
  it with a diagnosis, and moves on.
- Progress, attempt counts, and lessons live in `LOOP.md` (the ledger), not
  here.

Scope sources: AGENTS.md's known issues, and the "Open items roll-up
(2026-08-19)" that used to live in `docs/engine-comparison.md`. That roll-up
was retired along with the numbered TODO catalog in the same commit that
created this file; every item it listed appears below (as an item, or in
out-of-scope with a reason), so this file is now the record. Read it in the
history if you need the original wording: `git show 5163158830^:docs/engine-comparison.md`.

## V1 statement

V1 is done when: the known bugs below are fixed; the full e2e suite is green
without retries; the websocket suite carries no skips; the de-rtc
announce/commit inversion's verification debt is discharged;
`composer lint` is clean; a full fuzzer
matrix soak ends with every finding fixed or filed; and every Lane-B item has
a human-approved resolution (landed or explicitly deferred by the human).

## Lane B — human-review items

The loop may investigate, design, and implement these on a worktree branch,
but the result is a proposal (branch + written summary of what changed and
why + verification evidence), never a merge. The human approves, requests
changes, or defers.

### B1. yjs-server materialization fidelity (framework changes)

The framework-blocked half of the materialization-fidelity work:
yjs-server materialization still carries the Phase-2a wrapper
simplification — intent-log's twin was fixed by client-authored save
markup; the yjs path needs the same move in the framework (core-data
owns the Yjs block writer, `applyPostChangesToCRDTDoc`). The recorded
design: write `_wrapper`/`_save` entries into each
block's Y.Map from the same save-markup adapter; the engine's
`to_serializable_block` prefers in-doc entries over genesis wrappers.

**Proposal must include:** the subtree diff kept minimal and clearly bounded;
`cd gutenberg && npm run build` side-effects on tracked files reverted; the
full ladder green (`test:js`, `test:php`, `test:e2e`, `fuzz:quick`); and a
note on what the change implies for upstreaming (upstreaming itself is
human-owned and out of v1).

**Why Lane B:** framework edits change the pinned contract every engine runs
against, and the subtree eventually has to reconcile with upstream Gutenberg —
a judgment call about divergence cost.

### B2. Frozen-surface escalations (standing item)

Any change to: the frozen intent-log core (`src/engines/intent-log/**` except
additive `client.js` work, and its PHP twin), the frozen DE-RTC merge core
(`includes/engines/de-rtc/merge-core.php`), vendored `y-php` /
`automerge-php`, or the SEMANTICS of the frozen test vectors. The loop stops
at a written proposal: the smallest viable change, why no non-frozen
alternative exists, and how cross-language parity is re-certified (both vector
copies regenerated together, conformance suites green).

### B3. Pending-edit UI phase: inline block cards; panel goes summary-only

The validated prototype's decisions are recorded (two verbs
Adopt/Reject, one merged task per block, no version chip, panel becomes
summary-only with resolution at the inline block card). The behavior layer is
done; this is the editor-component UI that replaces the interim review-panel
routing.

**Why Lane B:** product-facing UX. The loop may build it to the prototype's
recorded decisions, but the human judges the result against the prototype
before merge. Verification evidence: Jest for the card lifecycle, an e2e
contested-edit walkthrough, `fuzz:quick` green.

### B4. Commit-cadence dial

Expose de-rtc's commit cadence (currently the settle cycle) as a setting with
the vision's 10-second operating point available. The inversion left it "a
setting away, not an architecture away."

**Why Lane B:** the default is a product decision (pseudo-realtime vs the
vision's cheap-host cadence changes what every de-rtc user experiences). The
proposal should include `save-sync-session` benchmark runs at both defaults.

### B5. Review resolutions over REST

The last mutating transport row: review RESOLUTIONS still ride transport rows.
Moving them to a REST review lane completes the strictest reading of the
transport-is-advisory inversion.

**Why Lane B:** a wire-protocol change (see escalation triggers — protocol
shape changes are Lane B by rule). Small, but it touches the session codec
contract and legacy-client behavior.

### B6. V1 sign-off

Human-only: review the ledger's parked/escalated list, approve or defer each
Lane-B proposal, merge the item branches, and declare v1. Any outward-facing
action (PRs, pushes to shared branches, upstream issues) is human-owned and
never part of the loop.

### F5. De-rtc: make the vendored Automerge library load-bearing (decision spike first)

Promoted from maybe item M1. The first bounded unit is phase 0, a
PHPUnit-only decision spike with explicit kill criteria — if it kills the
plan, F5 closes with the spike's evidence recorded and no further phases
run.

**Finding (2026-08-19).** The vendored `automerge-php` library never runs in
any live merge. `wp_de_rtc_get_automerge_native_port()` is the only thing that
constructs it, and it has one call site (`merge-core.php:1235`), reached only
when a proposal's `clientUpdate` is NOT in the `native-automerge-blocks-v1`
format. Every real path is block-native: our client stamps that format
(`src/engines/de-rtc/descriptor.ts:988,1017`), and the two `null`-update call
sites (`class-wp-de-rtc-engine.php:1320,1775`) get a server-derived update that
is also block-native. So merging is always
`wp_de_rtc_get_serialized_block_server_merge_result()`
(`merge-core.php:3164`) — a structural three-way merge over top-level
serialized blocks plus the rich-text merge model. The legacy whole-text lane
is dead even if reached: `NativePort::merge()` accepts only
document/last-edit pairs, so an operations-array update is rejected as
tampered (pinned by `tests/phpunit/wpDeRtcMergeCore.php:202`). The library's
only exercise is its own conformance suite and one round-trip unit test.

**This is upstream's shape, not our drift.** `merge-core.php` is a verbatim
port of wordpress-develop's `de-rtc.php`; Automerge there is a vocabulary and
tamper-evidence format (operations named `Automerge.Map.set`, hashes, change
ranges) rather than a merge runtime. Nothing is broken. The question is
whether we want the library to actually do work.

**Plan (server-only; the client keeps proposing whole content).**

0. **Decision spike.** PHPUnit-only: build an Automerge doc whose text carries
   block markers (`splitBlock`/`spans`/`updateSpans` — the port ships
   Automerge's rich-text block model), have two actors splice from the same
   heads, merge, materialize back to serialized blocks, and assert a clean
   parse/serialize round-trip with attributes intact. Micro-benchmark
   decode+apply+encode at 10/50/200 blocks against yjs-server's measured
   ingest. **Kill criteria:** per-proposal CPU worse than yjs-server, or block
   attributes/validity lost in the round-trip.
1. **Schema + adapter** in a NEW file (`includes/engines/de-rtc/automerge-lane.php`):
   serialized blocks ⇄ Automerge doc, doc persisted per room in a chained
   options row like the canonical content row, one actor per client, heads
   pinned per version.
2. **Last-chance merge lane.** Wire it in the engine (not the merge core) at
   the point where the block merger returns `de_rtc_rebase_failed`
   (`class-wp-de-rtc-engine.php:597`), before per-block salvage and before
   parking. Behind a filter, default off. This keeps `merge-core.php` verbatim
   and avoids the B2 frozen-surface escalation.
3. **Policy + tests.** Automerge resolves only concurrent text edits inside
   one block; attribute conflicts, delete-vs-edit, and move-vs-edit still
   park, because "genuine conflicts escalate instead of silently merging" is
   the engine's stated differentiator. Vectors, a fuzzer profile, benchmark
   deltas, `docs/engine-comparison.md` update.
4. **(Not recommended, out of any near-term scope.)** True op-based de-rtc:
   ship a JS Automerge in the client bundle and carry real changes on the
   wire. That is a protocol change (Lane B by rule) and effectively makes
   de-rtc a second CRDT engine alongside yjs-server.

**Estimate:** phases 0–3 ≈ 7–10 focused days, 4–6 loop cycles, with a real
chance phase 0 ends it. Phase 4 is multi-week and would be its own project.

**Risks (the reservations recorded at filing — why phase 0 may end it):**

- It fixes no known bug. The block merger works; this is a fidelity argument.
- It partly contradicts the engine's differentiator — a CRDT never escalates,
  so the value only exists in the narrow band of cases we park today.
- It makes a PHP 8.2 + mbstring floor load-bearing, and grapheme correctness
  varies below PHP 8.4 (PCRE2 < 10.43, two known conformance failures). Today
  that gate is optional, so none of it matters.
- Pure-PHP CRDT work per proposal lands in the engine that is meant to be the
  cheap-host option.
- It diverges from the upstream DE-RTC we currently track verbatim, and the
  divergence becomes ours to carry.

### F6. De-rtc: kses approval persistence (NEEDS SHAPING)

The rundown post's security section claims approved blocks "receive a
hash-pinned approval stamp and survive future edits, even by unprivileged
users." The implementation differs: the port deliberately dropped
upstream's kses-allowance periphery
(`includes/engines/de-rtc/class-wp-de-rtc-engine.php` header comment) —
approval is one-shot (a privileged restore re-proposes under the
restorer's capability), and the only survival path is the
byte-identical-to-base / kses-clean check in the sequester, so an
unprivileged edit to a block carrying previously-approved risky markup
likely re-parks it every time.

**First bounded unit (pre-shaping):** a PHPUnit reproduction — approve a
script-carrying block via restore, then have an unprivileged author
append text to it and observe whether it re-sequesters.
**Shaping decisions needed:** implement a per-block hash-pinned approval
allowance (upstream's model — engine-side, not the frozen merge core) OR
declare one-shot approval the policy and correct the post; where the
allowance persists (room meta vs content); how it interacts with the
review lane's re-propose semantics.

### F7. WebSocket advisory-channel transport mode (NEEDS SHAPING)

The rundown post presents the advisory channel as one of "two ways we
are exploring": the daemon delivers no updates, only
you-are-missing-updates notifications, and updates ride the ordinary
PHP worker pool via polling. Nothing advisory exists in the repo — the
shipped websocket transport is the relay (which post-A5 serves all
three engines). Foundations to build on: the A5 daemon room scan
(already a 1 Hz storage poll), and de-rtc's transport is already
advisory-shaped (announces/fetches on the wire, commits over REST).

**Shaping decisions needed:** protocol shape (cursor-bump broadcast vs
per-room dirty flag — a wire change, Lane B by rule); whether it is a
fourth transport or a daemon mode of the existing one; which engine
proves it first (de-rtc is the natural fit); acceptance = transport
benchmark A/B against the relay (edit-to-visible latency, idle traffic,
daemon cost per message) plus the fuzzer matrix on the new lane.

### F8. High-latency awareness primitives (NEEDS SHAPING)

The rundown post says "we are working to develop new primitives that
might be more appropriate for high-latency connections." Nothing in this
repo reflects that work — awareness is the retained user-level presence
model (avatars, arbitrary awareness data, server-verified identity)
across all engines and transports.

**Shaping decisions needed:** locate the work the post refers to
(possibly external/conceptual) and either import its requirements as a
design note or record the sentence as aspirational; define what
"high-latency-appropriate" means concretely (presence decay, cadence-
aware cursors, awareness over the F7 advisory channel); decide whether
any of it lands in this plugin or in the framework's awareness surface
(a framework edit would be Lane B by the subtree rule).

## Loop protocol (summary — the loop prompt is authoritative)

The scaffolding: `.claude/commands/v1-cycle.md` is the one-cycle
executor prompt (start the loop with `/loop /v1-cycle`),
`.claude/agents/v1-verifier.md` is the fresh-context verifier it
spawns, and `LOOP.md` is the ledger.

- Preflight every cycle: `npm run doctor`; fix or park on environment
  failures — uniform cross-engine timeouts are an environment problem.
- One ledger item per cycle, on branch `loop/<item-id>`, commits with
  `--no-verify`. Side discoveries become new ledger entries, never drive-bys.
- Suites are serialized: never `test:php` while e2e is in flight; one tests
  env consumer at a time.
- Maker is never grader: a fresh-context verifier confirms acceptance before
  an item is marked done.
- Stop rules: acceptance passed → next item; 3 strikes → park; budget
  exhausted → park cleanly; ledger empty → report and stop.
